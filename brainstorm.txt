# Cohort-Service API Specification

**Version:** 1.0
**Base path:** `/api/v1`
**Authentication:** Bearer access token issued by `identity-service`

## 1. Architecture and Responsibilities

The system consists of two independently owned services.

### Identity-service

Responsible for:
- People and institutional profiles.
- Account credentials and authentication.
- Access tokens, sessions, and refresh tokens.
- Profile status and institutional eligibility.
- Providing profile information to authorized internal services.

### Cohort-service

Responsible for:
- Cohort creation and lifecycle.
- Cohort ownership and membership.
- Cohort invitation codes.
- Direct membership invitations.
- Membership roles and authorization within cohorts.

Each service owns its database. Cohort-service stores institutional profile IDs as external references and must not query identity-service's database directly.

## 2. API Conventions

- Use `/api/v1` for API versioning.
- Use `name` in public API DTOs, mapped to the existing `Cohort.title` field.
- Use `status` in public API DTOs, mapped to `Cohort.state`.
- Derive the acting profile ID from trusted authentication context.
- Never trust a client-supplied profile ID to establish the caller's identity.
- Validate signed access tokens locally in cohort-service.
- Use Feign for identity lookups when profile validation or identity details are required.
- Apply authorization filters before pagination.
- Use UTC ISO-8601 timestamps.
- Return consistent JSON errors using Spring `ProblemDetail`.

### Identifier conventions

The internal cohort ID is the canonical identifier.

If a separate public identifier is required, introduce a `publicId` field. A hash or opaque public identifier is not an authorization mechanism.

The slug is human-readable and should be unique according to the chosen uniqueness scope. If the slug changes, define whether old URLs redirect or return `404 Not Found`.

The existing `Cohort` entity does not currently define `publicId` or a `parameters` field. Add them only if required by the product.

## 3. Cohort Management Endpoints

### 3.1 Create a cohort

`POST /api/v1/cohorts`

**Authorization:** Authenticated, eligible `FACULTY` profile.

Request:

```json
{
  "name": "Introduction to Computer Science",
  "slug": "intro-computer-science",
  "description": "First-year computer science cohort",
  "status": "DRAFT",
  "parameters": {}
}
```

Rules:
- `name` is required, between 1 and 255 characters.
- `slug` may be generated from the name if omitted.
- `description` is optional, maximum 1024 characters.
- `status` defaults to `DRAFT`.
- Clients cannot create a cohort directly in `ACTIVE` or `ARCHIVED`.
- The caller's profile ID becomes `ownerProfileId`.
- The owner should receive a `FACULTY` membership if owners are expected to participate as cohort members.

Response: `201 Created`.

```json
{
  "id": "internal-cohort-uuid",
  "publicId": "cohort-public-id",
  "name": "Introduction to Computer Science",
  "slug": "intro-computer-science",
  "status": "DRAFT",
  "description": "First-year computer science cohort",
  "createdAt": "2026-10-19T18:00:00Z",
  "parameters": {}
}
```

### 3.2 List cohorts

`GET /api/v1/cohorts`

**Authorization:** Authenticated user. Results are restricted to cohorts the caller is authorized to discover.

Query parameters:

| Parameter | Description |
|---|---|
| `status` | Filter by `DRAFT`, `ACTIVE`, or `ARCHIVED` |
| `createdAfter` | Inclusive lower creation timestamp |
| `createdBefore` | Inclusive upper creation timestamp |
| `mine` | Restrict to cohorts owned by the caller |
| `page` | Zero-based page number |
| `size` | Page size, with a configured maximum |
| `sort` | Supported sorting field and direction |

Example:

`GET /api/v1/cohorts?status=ACTIVE&page=0&size=20`

Response: `200 OK`.

```json
{
  "content": [
    {
      "id": "internal-cohort-uuid",
      "publicId": "cohort-public-id",
      "name": "Introduction to Computer Science",
      "slug": "intro-computer-science",
      "status": "ACTIVE",
      "description": "First-year computer science cohort",
      "createdAt": "2026-10-19T18:00:00Z",
      "parameters": {}
    }
  ],
  "page": 0,
  "size": 20,
  "totalElements": 1,
  "totalPages": 1
}
```

Apply visibility filters before pagination and calculate totals from the authorized result set.

### 3.3 Retrieve a cohort

`GET /api/v1/cohorts/{cohortId}/{slug}`

**Authorization:** Authenticated user who is a member of the cohort, unless public or institution-wide discovery is explicitly supported.

Rules:
- The cohort ID must exist.
- The supplied slug must match the cohort's current slug.
- Return `404 Not Found` if the ID or slug does not match.
- Define whether archived cohorts remain readable.

Response: `200 OK`, using the standard cohort representation.

### 3.4 Update cohort metadata

`PUT /api/v1/cohorts/{cohortId}`

**Authorization:** Eligible `FACULTY` profile who owns the cohort.

Request:

```json
{
  "name": "Introduction to Computer Science — 2026",
  "slug": "intro-computer-science-2026",
  "description": "Updated cohort description",
  "parameters": {}
}
```

Rules:
- Update only editable metadata.
- Status changes must use the dedicated status endpoint.
- Validate slug uniqueness.
- Define whether metadata can be changed after activation.

Response: `200 OK`, with the updated cohort representation.

### 3.5 Change cohort status

`PATCH /api/v1/cohorts/{cohortId}/status`

**Authorization:** Eligible faculty owner.

Request:

```json
{
  "status": "ACTIVE"
}
```

Recommended transitions:

| Current status | Allowed next status |
|---|---|
| `DRAFT` | `ACTIVE`, `ARCHIVED` |
| `ACTIVE` | `ARCHIVED` |
| `ARCHIVED` | `ACTIVE`, only if reactivation is supported |

Reject invalid transitions with `409 Conflict`.

Response: `200 OK`, with the updated cohort representation.

### 3.6 Delete a cohort

`DELETE /api/v1/cohorts/{cohortId}`

**Authorization:** Faculty owner.

Rules:
- The cohort must be in `DRAFT`.
- Define how dependent memberships and invitations are handled.
- Do not delete unrelated identity data.
- Consider preventing deletion when dependent records exist.

Response: `204 No Content`.

## 4. Cohort Invitation Codes

Invitation codes allow eligible profiles to join an active cohort without a direct invitation.

### 4.1 Generate an invitation code

`POST /api/v1/cohorts/{cohortId}/invitation-code`

**Authorization:** Faculty member of an `ACTIVE` cohort.

Request:

```json
{
  "expiresAt": "2026-11-19T18:00:00Z"
}
```

`expiresAt` is optional. The server should validate the timestamp and enforce any configured maximum lifetime.

Response: `201 Created`.

```json
{
  "code": "random-high-entropy-code",
  "expiresAt": "2026-11-19T18:00:00Z",
  "cohort": {
    "publicId": "cohort-public-id",
    "name": "Introduction to Computer Science",
    "slug": "intro-computer-science",
    "status": "ACTIVE"
  }
}
```

Rules:
- Only one effectively active code may exist per cohort.
- Expired or revoked codes must not prevent creating a replacement.
- Generate codes using a cryptographically secure random generator.
- Prefer storing a hash of the code rather than retrievable plaintext.
- If plaintext cannot be recovered, return the raw code only at creation time.
- Enforce concurrency safety using database constraints or appropriate locking.

### 4.2 Retrieve invitation-code information

`GET /api/v1/cohorts/{cohortId}/invitation-code`

**Authorization:** Faculty member of an `ACTIVE` cohort.

Return code metadata, expiry, and effective state. If raw codes are stored only as hashes, do not return the original code; provide a replacement flow instead.

Response: `200 OK`.

Return `404 Not Found` if no valid code exists.

### 4.3 Revoke an invitation code

`DELETE /api/v1/cohorts/{cohortId}/invitation-code`

**Authorization:** Faculty member of an `ACTIVE` cohort.

Rules:
- A code must exist.
- Revocation must be persisted transactionally.
- Subsequent join attempts must fail.

Response: `204 No Content`.

## 5. Direct Membership Invitations

Direct invitations are distinct from reusable invitation codes.

A direct invitation targets a specific institutional profile and must not depend on the existence of a cohort invitation code.

### Recommended entity additions

Add explicit lifecycle state and expiration fields to `CohortMembershipInvitation`.

```kotlin
enum class MembershipInvitationState {
    PENDING,
    ACCEPTED,
    REJECTED,
    REVOKED,
    EXPIRED
}
```

Suggested fields:

```kotlin
@Enumerated(EnumType.STRING)
@Column(nullable = false, length = 20)
var state: MembershipInvitationState =
    MembershipInvitationState.PENDING

@Column
var expiresAt: Instant? = null

@Column
var revokedAt: Instant? = null
```

Keep existing timestamps if needed for audit purposes, and define valid state transitions.

### 5.1 Send an invitation

`POST /api/v1/cohorts/{cohortId}/invitations`

**Authorization:** Faculty member of an `ACTIVE` cohort.

Request:

```json
{
  "profileId": "institutional-profile-uuid",
  "role": "STUDENT",
  "expiresAt": "2026-11-19T18:00:00Z"
}
```

Rules:
- Validate the target profile through identity-service.
- Target profiles must be eligible students or faculty.
- Validate that the requested cohort role is compatible with the profile type.
- Reject duplicate pending invitations.
- Define the policy for inviting existing members.
- The inviter ID must come from authenticated context.

Response: `201 Created`.

```json
{
  "id": "invitation-uuid",
  "cohortId": "cohort-uuid",
  "profileId": "institutional-profile-uuid",
  "role": "STUDENT",
  "status": "PENDING",
  "invitedAt": "2026-10-19T18:00:00Z",
  "expiresAt": "2026-11-19T18:00:00Z"
}
```

### 5.2 List invitations

`GET /api/v1/cohorts/{cohortId}/invitations`

**Authorization:** Faculty member of an `ACTIVE` cohort.

Return a paginated list of invitations enriched with authorized identity information.

Recommended fields:

- `profileId`
- `displayName`
- `login`
- `email`
- `profileType`
- `role`
- `status`
- `invitedAt`
- `expiresAt`

Identity details must come from identity-service rather than being copied into the invitation entity.

### 5.3 Revoke an invitation

`DELETE /api/v1/cohorts/{cohortId}/invitations/{profileId}`

**Authorization:** Faculty member of an `ACTIVE` cohort.

Rules:
- The target must have a pending invitation.
- Only pending invitations can be revoked.
- Accepted invitations must be handled through membership removal.

Response: `204 No Content`.

### 5.4 Accept an invitation

Recommended endpoint:

`POST /api/v1/cohorts/{cohortId}/invitations/accept`

**Authorization:** The authenticated profile must own the pending invitation.

The target profile ID should be derived from authentication context rather than supplied by the client.

Rules:
- The cohort must be active.
- The invitation must be pending and unexpired.
- The profile must remain eligible.
- Membership creation and invitation acceptance must be atomic.
- Repeated acceptance should be idempotent according to a documented policy.

Response: `201 Created` for a new membership, or `200 OK` for an idempotent repeat.

## 6. Joining Through an Invitation Code

### 6.1 Join a cohort

`POST /api/v1/cohort-invitation-codes/{code}/join`

**Authorization:** Authenticated, eligible student or faculty profile.

No profile ID is required in the request body. The server derives the acting profile from authentication context.

Rules:
- The code must be valid, unexpired and not revoked.
- The cohort must be active.
- The profile must be eligible.
- The membership role must be determined by server-side domain rules.
- Prevent duplicate active memberships.
- If a previous membership exists with `leftAt` set, define reactivation behavior.
- Rate-limit join attempts.

Response: `201 Created`.

```json
{
  "cohortId": "cohort-uuid",
  "profileId": "authenticated-profile-uuid",
  "role": "STUDENT",
  "joinedAt": "2026-10-19T18:00:00Z"
}
```

## 7. Membership Endpoints

### 7.1 List cohort members

`GET /api/v1/cohorts/{cohortId}/members`

**Authorization:** Current member of an `ACTIVE` cohort.

Response: `200 OK`.

```json
{
  "content": [
    {
      "profileId": "institutional-profile-uuid",
      "displayName": "Taylor Example",
      "profileType": "STUDENT",
      "role": "STUDENT",
      "joinedAt": "2026-10-19T18:00:00Z"
    }
  ],
  "page": 0,
  "size": 20,
  "totalElements": 1,
  "totalPages": 1
}
```

Return only current members by default. Use identity-service batch lookup to enrich profile details.

### 7.2 List faculty members

`GET /api/v1/cohorts/{cohortId}/faculty`

**Authorization:** Current member of an `ACTIVE` cohort.

Return current members whose cohort role is `FACULTY`.

Use the same pagination and response structure as the members endpoint.

Define whether faculty is determined by `CohortMembership.role`, `InstitutionalProfile.type`, or both. Enforce compatibility when assigning membership roles.

### 7.3 Remove a member

`DELETE /api/v1/cohorts/{cohortId}/members/{profileId}`

**Authorization:** Faculty member of an `ACTIVE` cohort.

Rules:
- The target must have an active membership.
- Set `leftAt` rather than deleting the membership history.
- Define whether faculty can remove themselves.
- Prevent removing the last faculty member if every active cohort requires faculty supervision.
- Require ownership transfer before removing the owner, if applicable.

Response: `204 No Content`.

## 8. Identity-Service Integration Contract

The supplied identity-service entities contain the information required for most cohort operations. The following endpoints are proposed contracts and must be implemented if they do not already exist.

### 8.1 Retrieve one institutional profile

`GET /api/v1/profiles/{profileId}`

Example response:

```json
{
  "profileId": "institutional-profile-uuid",
  "personId": "person-uuid",
  "type": "FACULTY",
  "state": "ACTIVE",
  "profileActive": true,
  "credentialActive": true,
  "displayName": "Alex Example",
  "email": "alex@example.edu",
  "login": "alex@example.edu"
}
```

The response can be assembled from:

- `InstitutionalProfile.id`
- `InstitutionalProfile.type`
- `InstitutionalProfile.state`
- `InstitutionalProfile.active`
- `InstitutionalProfile.email`
- `Person.displayName`
- `AccountCredential.login`
- `AccountCredential.active`

Do not collapse profile activity, institutional state and credential activity into one ambiguous flag.

### 8.2 Batch profile lookup

`POST /api/v1/profiles/batch-lookup`

Request:

```json
{
  "profileIds": [
    "profile-uuid-1",
    "profile-uuid-2",
    "profile-uuid-3"
  ]
}
```

Response:

```json
{
  "profiles": [
    {
      "profileId": "profile-uuid-1",
      "type": "STUDENT",
      "state": "ACTIVE",
      "profileActive": true,
      "credentialActive": true,
      "displayName": "Taylor Example",
      "email": "taylor@example.edu",
      "login": "taylor@example.edu"
    }
  ],
  "notFoundProfileIds": [
    "profile-uuid-3"
  ]
}
```

Requirements:
- Enforce a maximum batch size.
- Apply service authentication and field-level authorization.
- Return only the fields required by cohort-service.
- Support partial results for unknown IDs.
- Avoid N+1 HTTP calls when listing members and invitations.

### 8.3 Optional caller-profile endpoint

`GET /api/v1/profiles/me`

Useful if identity-service supports a selected institutional profile in the user's authentication context.

If a person can have multiple profiles, define how the active profile is selected. Cohort-service should not guess the acting profile from a person ID alone.

### Identity-service contract gaps

Before integration, confirm:

1. Whether access tokens contain the selected institutional profile ID.
2. Whether token claims distinguish person ID, credential ID and profile ID.
3. Whether the issuer exposes public keys for JWT verification.
4. How inactive profiles and disabled credentials affect access.
5. Whether profile lookup endpoints already exist.
6. Whether internal service-to-service authentication is configured.
7. Whether profile type and status enums use string persistence.

Use `@Enumerated(EnumType.STRING)` for `InstitutionalProfile.type` and `InstitutionalProfile.state`. The current default ordinal mapping is fragile if enum values are reordered.

## 9. Feign Client

A minimal Spring Cloud OpenFeign interface can look like this:

```kotlin
@FeignClient(
    name = "identity-service",
    url = "\${clients.identity-service.url}"
)
interface IdentityClient {

    @GetMapping("/api/v1/profiles/{profileId}")
    fun getProfile(
        @PathVariable profileId: String
    ): InstitutionalProfileResponse

    @PostMapping("/api/v1/profiles/batch-lookup")
    fun getProfiles(
        @RequestBody request: ProfileBatchLookupRequest
    ): ProfileBatchLookupResponse
}
```

Suggested integration DTOs:

```kotlin
data class InstitutionalProfileResponse(
    val profileId: String,
    val type: String,
    val state: String,
    val profileActive: Boolean,
    val credentialActive: Boolean,
    val displayName: String,
    val email: String,
    val login: String?
)

data class ProfileBatchLookupRequest(
    val profileIds: List<String>
)

data class ProfileBatchLookupResponse(
    val profiles: List<InstitutionalProfileResponse>,
    val notFoundProfileIds: List<String>
)
```

These DTOs belong to the cohort-service integration layer, not the identity-service JPA entity package.

### Feign requirements

- Validate signed JWTs locally rather than calling identity-service for every request.
- Configure issuer, audience, expiry and signature verification.
- Use explicit service-to-service authentication for internal profile lookups.
- Set connection and read timeouts.
- Use bounded retries and avoid blindly retrying non-idempotent operations.
- Fail closed if profile eligibility cannot be established.
- Keep remote calls outside long-running database transactions when possible.
- Avoid returning unnecessary personal information.
- Consider caching profile lookups only with a clear invalidation strategy.

For high-volume reads, an event-driven profile projection can be introduced later. Feign is a sensible initial approach.

## 10. Entity Changes

| Entity | Recommended change |
|---|---|
| `Cohort` | Add `publicId` only if a separate public identifier is needed |
| `Cohort` | Map public API `name` to internal `title` |
| `Cohort` | Add `parameters` only when a concrete schema and use case exist |
| `CohortMembership` | Add a unique constraint on `(cohort_id, profile_id)` |
| `CohortMembership` | Define rejoining and `leftAt` semantics |
| `CohortMembershipInvitation` | Add explicit state, expiry and revocation semantics |
| `CohortInvitationCode` | Define hash storage, expiry behavior and single-active-code enforcement |
| `InstitutionalProfile` | Persist enums using `EnumType.STRING` |
| `AccountCredential` | Enforce normalized login uniqueness and store only password hashes |
| `AccountTrait` | Add a trait key/name to distinguish different attributes |

The existing globally unique slug constraint is appropriate only if slugs must be unique across the entire service. If uniqueness is tenant- or institution-specific, adjust the constraint accordingly.

## 11. Error Contract

Use consistent error responses, preferably through Spring `ProblemDetail`.

| HTTP status | Meaning |
|---|---|
| `400 Bad Request` | Malformed input or invalid filter |
| `401 Unauthorized` | Missing or invalid access token |
| `403 Forbidden` | Insufficient permissions |
| `404 Not Found` | Resource not found or intentionally hidden |
| `409 Conflict` | Invalid state transition, duplicate membership or active code conflict |
| `410 Gone` | Expired or revoked code, if distinguished from not found |
| `429 Too Many Requests` | Rate limit exceeded |
| `502 Bad Gateway` / `503 Service Unavailable` | Identity dependency failure |

Example:

```json
{
  "type": "about:blank",
  "title": "Conflict",
  "status": 409,
  "detail": "The cohort cannot transition from ARCHIVED to DRAFT.",
  "instance": "/api/v1/cohorts/cohort-uuid/status"
}
```

Never expose SQL errors, internal exception messages or sensitive identity information.

## 12. Implementation Priorities

### Phase 1 — Core cohorts
- JWT validation and profile context.
- Create, list, retrieve, update, status change and draft deletion.
- Owner membership creation.
- Slug and membership uniqueness constraints.

### Phase 2 — Identity integration
- Profile lookup endpoint.
- Batch lookup endpoint.
- Feign configuration and service authentication.
- Eligibility validation and error handling.

### Phase 3 — Membership and invitations
- Direct invitation lifecycle.
- Invitation-code generation, retrieval and revocation.
- Join and accept operations.
- Member and faculty listings.
- Member removal and rejoining rules.

### Phase 4 — Hardening
- Concurrency-safe code generation and membership creation.
- Rate limiting.
- Audit logging.
- Profile deactivation handling.
- Optional caching or event-driven profile projections.

## 13. Final Architectural Principle

**Identity-service establishes who a profile is and whether it is eligible. Cohort-service determines what that profile can do within a cohort.**

Maintain separate database ownership, validate tokens locally, use Feign for profile validation and enrichment, and enforce membership and invitation rules transactionally. This gives you a clean initial architecture without introducing unnecessary infrastructure.
